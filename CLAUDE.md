# DevHub : règles pour Claude

## Où tourne DevHub
- DevHub tourne **uniquement dans des conteneurs Docker**, et **un seul conteneur pour DevHub** : `devhub`, qui contient le panel et Caddy (lancé et surveillé par DevHub, `src/caddy.rs`, fichiers dans l'image sous `/etc/caddy`). Il est sur le réseau du serveur (`network_mode: host`) et joint les projets par l'adresse de leur conteneur (`docker::Reach::Address`). Les projets ont chacun leur conteneur (`devhub-<nom>`), et les tâches ponctuelles (installation, mise à jour, passage sur un domaine) tournent dans des conteneurs temporaires.
- **Rien sur le serveur en dehors de Docker** : pas de dossier, pas de `.env`, pas de copie Git. La base est dans le volume `devhub-data`, les certificats dans `devhub-caddy`, les réglages sont les variables du conteneur `devhub`. Le conteneur est créé ou remplacé par `devhub deploy` (`src/deploy.rs`), lancé dans un conteneur temporaire par l'installateur, par la mise à jour (image `ghcr.io/…:<commit>`, version lue dans `DEVHUB_REVISION`) et par les changements de réglages (`updater::reconfigure`).
- Anciennes installations (docker compose dans `/opt/devhub`) : elles passent seules dans les volumes après la mise à jour (`updater::migrate_once`). `docker-compose.yml`, `docker-compose.ip.yml` et `caddy/Dockerfile` ne restent que pour elles : leur ancienne mise à jour fait encore `git pull` + `docker compose up -d` une fois. Ne pas les supprimer, et ne pas modifier `caddy/Dockerfile` (l'ancienne mise à jour reconstruirait un service `caddy` qui n'existe plus).
- Rien d'autre ne s'installe ni ne tourne sur le VPS que Docker lui-même : pas de binaire, de service systemd, de paquet ou de règle système ajoutés par DevHub. Une nouvelle fonction qui a besoin de l'hôte passe par un montage ou par le socket Docker, jamais par un programme installé sur le VPS.
- Installation : `docker run --rm -it -v /var/run/docker.sock:/var/run/docker.sock ghcr.io/tweastly/devhub`, sans aucun montage d'un dossier du serveur. L'image s'installe elle-même : lancée sans réglages avec le socket, elle exécute `devhub install` (`src/install.rs`) ; son point d'entrée est `devhub`. `install.sh` (pour `curl | sh`) installe seulement Docker s'il manque puis lance la même chose ; `:install` est un alias de l'image démarrant sur l'installateur. Commande longue documentée aussi (`docker run -d --name devhub --network host …`) : nommée `devhub`, l'image se reconnaît comme le panel (`install::panel_defaults`, IP publique détectée) au lieu de lancer l'installateur.
- L'installation se fait dans le navigateur, pas dans la console : `install.sh` ne pose aucune question (seulement installer Docker s'il manque), démarre DevHub sur l'IP du serveur et affiche l'adresse de `/setup` et le code. Le guide web (`src/web/setup.rs`) demande ensuite le nom de domaine, vérifie le DNS (ou crée les enregistrements chez Cloudflare) et fait passer DevHub sur le domaine (`updater::switch_domain` → `devhub deploy --env DEVHUB_DOMAIN=…`). Le code d'installation est gardé dans les réglages (`setup_code`) jusqu'à la création du propriétaire. Le guide ne revient jamais une fois l'installation finie (réglage `setup_done`, posé par « Configurer plus tard », la page de fin ou le tableau de bord) : `/setup` mène alors au tableau de bord, chaque réglage a sa page. Pas de lien vers le guide dans le menu, pas de page Paramètres qui doublonne les autres.
- Page **Adresse et domaine** (`/address`, `src/web/address.rs`) : passer de l'IP à un domaine (mêmes étapes que le guide) et d'un domaine à l'IP (`address::to_ip`). Sans mot de passe, le propriétaire en choisit un sur l'IP avec un code d'installation emporté par la page. Au passage sur l'IP, DevHub recrée les projets qui publiaient leurs ports web (`caddy::release_web_ports`), sinon Caddy ne pourrait pas les écouter.

## Avec ou sans nom de domaine
- Avec un domaine : passkeys, un sous-domaine par projet (`caddy/Caddyfile`).
- Sans domaine, mode « IP seule » (`DEVHUB_DOMAIN` = une IP, `cfg.ip_mode`) : connexion par mot de passe (les passkeys refusent une IP), un port par projet web (`https://IP:20000`…), `caddy/Caddyfile.ip` (DevHub calcule `DEVHUB_IP_SITES`). Un projet peut quand même avoir son propre nom de domaine (onglet Réseau, nom complet) : Caddy le sert sur le 443 avec un certificat à la première visite (bloc `https://` de `Caddyfile.ip`). `docker-compose.ip.yml` ne reste que pour les anciens `.env` qui le citent.

## Accès au VPS
- DevHub a la main sur le VPS depuis son conteneur, pour piloter les projets (socket Docker) et lire les statistiques du serveur (CPU, mémoire, disque, durée de fonctionnement…).
- Le MCP (assistants IA) n'a pas cet accès à l'hôte : ses outils restent limités aux projets et aux réglages de DevHub. Pas de commande, de fichier ni de contrôle sur le VPS lui-même par le MCP.
